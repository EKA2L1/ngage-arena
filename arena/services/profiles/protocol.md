# Profiles protocol

### N-Gage 2.0 shared profiles

`/ngi/axis/services/userprofile` accepts the native SOAP profile operations. Operation and response roots use their individual `http://www.nokia.com/ngp/...` namespaces; their children are unqualified. The schema metadata in `nafuserprofile.dll` defines ordered sequences and response choices. For example, `getMiniProfileResponse` contains either `miniProfile` or `ngpexception`; `getProfileResponse` has optional `user` and `ngpException`, with different capitalization. The profile request uses `lastSynchDate`, while the friends request uses `lastSyncDate`.

`arena.services.profiles.service` stores profiles, game history and friendship relationships against the canonical account IDs in the same SQLite database. Full profile reads and updates use the authenticated HTTP session, never a supplied username. Mini-profiles contain the username, icon URL, three N-Gage point categories and game history; their endpoint also requires login. Friend details require an accepted relationship. Writes are validated before committing and preserve other games' history and the account's credentials. Mini-profile and game-history points come from the achievement journal, as do the point boards. The native game-history upload can contain only an application UID; registered adapters map that UID to the achievement game class. Self-reported profile totals are retained as input history but do not determine displayed points. Dates and points without a source remain unset or zero. Custom icon selection/upload, reputation calculation and password recovery are still incomplete.

The native Launcher completed the profile request sequence, uploaded four installed games' last-played timestamps and saved an edited Motto through `updateProfile`. The native update includes `alertSubscription`, `privacySetting`, `ignoreUsersList`, `newsLetterSubscription`, `games` and `userIcon`; an empty built-in icon uses type `ASSET`. The returned `timeStamp` advances its subsequent synchronization requests. Server-side Motto changes were displayed with both a clean cache and the restored original cache after its pending upload completed.

The Launcher gives pending local changes precedence over downloaded editable fields. `playservermp.dll` stores `LocalProfileChanged` in its `LoginTable`. The profile response handler at linked address `0xb56e` tests this flag through `0x90fc`: the dirty branch retains editable local values and proceeds to upload, while the clean branch applies the downloaded profile. Successful upload completion at `0xb6b2` saves the timestamp and clears the flag at `0xb6bc`. A stale local Motto overwriting a server edit after offline gameplay was reproduced, then distinguished from a parser failure through the two download controls. The server follows this native whole-profile update policy; it does not claim field-level conflict merging.

The authentication server sends a plain HTTP GET availability probe to `/ngi/axis/services/NGICommunity` about every ten minutes. The native request contains only Host and User-Agent headers, with no cookie, query or matrix session identifier. Its `HeartBeatUtl` response callback at `0xa124` in `NAFAuthSrvr_V3` treats HTTP 401 as lost authentication. The service returns an empty HTTP 200 response without creating, authenticating or refreshing any account session. Treating this anonymous probe as session validation incorrectly logs the native client out. Authenticated SOAP operations continue to enforce their session requirements and expiry. The native timer clamps a configured interval below 60 seconds to 60 seconds (`0x897c`–`0x898c`).

### Default profile icon and live notifications

Profiles without an icon return a URL for the original 64×64 PNG in this module's `assets/` directory. `/ngi/assets/avatar.png` supports public HEAD and GET with matching MIME type and content length, without creating or extending account sessions. The URL uses the profile request's Host, port and HTTP/HTTPS transport, so existing emulator host overrides also apply to the asset. Explicit profile icon URLs remain intact; selecting and uploading custom icons is separate work.

An empty `iconUrl` prevents the native Launcher from publishing some live friend events. In `playservermh.dll`, a new invitation is inserted into `MessagesTable` at `0xb160`, then requests the sender's mini-profile at `0xb4d2`. The mini-profile callback at `0xca40` updates the user and tries to load its icon through `0xab50`. That helper returns zero for URLs shorter than four bytes without starting an operation; the caller interprets zero as a pending download and omits the notification. Successful image completion reaches `0xe208` / `0xc202`, which finally notifies the UI. Full roster replies cannot replace this callback.

The icon download exposed a separate emulator gap: DownloadMgrServer synchronously calls AppArc `AppForDataType` (opcode 14), with a packaged `TDataType` in slot 0 and output UID in slot 1. Dropping that request stalls image storage and the same notification chain. EKA2L1 must complete the query using registered MIME handlers, or a null UID when no handler exists, as specified by `APGCLI.CPP`, `APSSES.CPP` and `CApaAppList::PreferredDataHandlerL` in Symbian AppArc. No Launcher DLL patch is needed.
