# Friends and messaging validation

## Launcher friends and shared points — 14 September 2026

Two original Launchers on the same final Release simulator executable used shared accounts `adgjmptw` and `wtpmjgda`. The sender's native Add Friend form submitted an invitation while the recipient was offline. After login, the recipient opened New Messages, displayed the original invitation text and chose Accept. Its native reciprocal subscription carried status `1`; the original sender automatically accepted that request after logging in again. Both directed relationships persisted as accepted, and both Launchers displayed the other account in Friends. The recipient also displayed the native notification that `adgjmptw` was now available to play. No friendship was inserted into the database by a fixture or debugger.

Native online chat was then confirmed in both directions: each original Launcher displayed the other account's body. For offline delivery, the sender queued `Offline paced 0012` while the recipient was stopped. The recipient's first local-server attempts fetched and purged correctly formed messages without displaying them. Outgoing XMPP capture and binary inspection showed that the Launcher pipelines roster and mailbox requests, while `nafimpssrvr_v3.dll` drops a message if PlayServer has not yet created its friend object. The loopback server was responding before that callback completed. Delaying a nonempty fetch by one second let the original client store the body, changed Home from one built-in message to two, and displayed `wtpmjgda: "Offline paced 0012"` in New Messages. The matching server row was removed by the native purge. `native-offline-message.jpg` and the guest database provide the visual and persisted evidence.

Offline messages now carry unique second-resolution UTC `jabber:x:delay` stamps; header nodes use the same value and malformed selectors are rejected. Client-supplied delay elements are replaced. Fetches can repeat until purge, and purge removes only that connection's fetched batch, preserving later or unrelated messages. Automated coverage includes same-second uniqueness, literal legacy XML element names, pacing, database reopening and malformed nodes.

Friend mini-profiles initially returned zero points from client-uploaded game history even though the achievement and global point boards held 30. The shared profile read now uses the same earned-point ledger. Native game history supplies only the application UID, so the registered game's `app_uid` maps it to the achievement class. The original friend card now displays account 1 with **30 N-Gage Points**; authenticated friend-profile and anonymous global-board probes return the same **0 solo / 30 multiplayer / 0 community** values.

All **179 service tests** completed successfully with the final code. Added coverage includes directional grants, offline invitations, reciprocal acceptance, removal and rejection, presence revocation, blocked accounts, shared game-domain identities, sender authentication, selective and repeated offline fetches, delayed purge from another resource, roster-callback pacing, database reopening, and profile/board point consistency. Temporary outgoing packet tracing was removed. There are no emulator changes in this step, so the recorded Release, Qt and Android checks remain applicable. Evidence is under `data/verification/friends-2026-09-14/`.

A later native Remove from Friends List deleted both directed grants. After cold login the other Launcher displayed the removal notification, confirming persistence. Native reinvitation after removal remained pending in the service but did not appear in the recipient UI; rejection and this reinvitation path remain unverified. XcodeBuildMCP and AXE completed login, password entry, friend-point inspection, bidirectional chat and offline-message display while macOS was locked. Mac unlock is not a prerequisite for iOS Simulator interaction.
