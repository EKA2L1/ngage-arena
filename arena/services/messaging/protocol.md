# Friends and messaging protocol

### Native friend subscriptions and messages

`arena.services.messaging.service` implements the local-account subset of XMPP roster and presence subscriptions. Grants are directional, following [RFC 6121](https://xmpp.org/rfcs/rfc6121.html): sending `subscribe` creates a pending request; `subscribed` grants the requester's access to presence. A mutual friendship has both grants. Roster edits cannot grant subscriptions. Cancellation revokes the corresponding grant and visible presence; removing a roster item revokes both directions. Contacts survive subscription cancellation until explicitly removed. No external XMPP federation is provided.

The original Launcher sends invitation ID `segachat_buddy_req` with a status body beginning with `0`, followed by invitation text. After acceptance it sends `segachat_buddy_accrej` and a reciprocal subscription with status `1`. The receiver's native IMPS handler automatically accepts that reciprocal request. In `nafsclib_v3.dll`, `0xc458` parses the first status character; `nafimpssrvr_v3.dll` handles the resulting buddy request at `0xb4d8`. The server preserves these opaque status values rather than silently granting both directions. Pending invitations persist across disconnects and database reopening.

Native chat messages have neither a `type` nor an `id` attribute and carry a body such as `0001Hello`. `nafsclib_v3.dll`'s message handler at `0xd818` rejects a message with a `type` attribute and directs identified messages to other callbacks. Forwarding preserves this envelope and body while deriving the sender from the authenticated connection. Available local resources receive messages immediately; otherwise the recipient's bounded mailbox retains them. Blocking is checked at submission and retrieval.

The Launcher asks for offline headers using `disco#items` with node `http://jabber.org/protocol/offline` and an optional sender JID. Its header parser at `0xca6c` requires a `count` matching the number of items; each item supplies sender `jid` and message `node`. Stored messages receive a unique UTC `jabber:x:delay` stamp, and that stamp is also the header node. The native message handler reads the literal `x` element and its `stamp` attribute. It then sends `action="fetch"`, either with that JID/node or without filters, followed by `action="purge"`.

The Launcher pipelines these requests before PlayServer finishes applying the roster callback. A loopback server can return the message while its sender has no native friend object, causing `nafimpssrvr_v3.dll` at `0xb1a6` to discard it even though the client later purges it. Nonempty fetches therefore wait one second before delivery. Fetches remain scoped to the authenticated recipient and can be repeated until explicit purge, matching the retained-message behavior used by this XEP subset. Purge removes only that connection's fetched batch, preserving messages received later. Unconfirmed messages survive reconnects. This is the observed SNAP dialect, not a claim of complete XEP-0013 support.

Native invitation acceptance, reciprocal friendship, earned friend points and bidirectional online chat have been observed on two original clients. A native offline message was stored, fetched, displayed with its sender and body, and purged. Native removal and its notification after recipient restart also passed. Rejection and reinvitation after removal remain pending. See [validation](validation.md).
