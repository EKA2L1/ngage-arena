# N-Gage Arena client protocols

## Tomb Raider AirPlay

This document records the implemented subset of the original N-Gage client protocol. It is derived from the installed ARM binaries and native client exchanges. It is not a specification of the retired Nokia service. Names such as `DecryptAndDispatchMessageL` in the client do not imply encryption: this transport sends these fields directly over UDP.

## Transport

All integers are little-endian. Each UDP datagram starts with `u32 sequence, u8 command, u8 flag, u16 extra`. A packet with flag 0 requires command 250, flag 1, with the acknowledged sequence as a four-byte body. Sequences suppress duplicates. The server limits outstanding replies to four and retries with backoff. A short initial response delay allows the client's separate network and UI IPC requests to finish arming on localhost.

Strings are `u32 byte_length` followed by that many Latin-1 bytes. They are not null-terminated. The server does not log login strings. It stores an HMAC of the emulated device identity, with a private per-database key, to associate subsequent logins with the same local account.

| Request | Body | Reply |
| --- | --- | --- |
| 50 | `u16`, provider version string, MD5 string, two `u16`, identity string, string | 150: status byte and string; status 1 requests a provider update |
| 51 | empty | 121: provider DLL chunks |
| 0 | five `u16`, game string, `u32`, nickname, password, device identity, subscriber identity, `u8` | 120: login status and auxiliary byte |
| 2 | nickname, device identity | 120: login/rename status |
| 1 | disconnect | no application reply |
| 9 | `u32 parent`, filter string | 124: directory pages |
| 10 | empty | 125: an empty event page |
| 11 | filter string | 126: message pages |
| 3 | `u32 object_id`, token string | 121: content chunks |
| 6 | `u16 type`, `u32 size`, caption string, two `u32` values | 122: begin sending chunks |
| 7 | target string, `u32 size`, caption string, two `u32` values | 122: begin sending clip chunks |
| 8 | `u32 start`, inclusive end, chunk size, bytes | 123 after the complete validated upload is persisted |
| 12 | eight timestamp bytes | 127: the same eight bytes |

Type 1001 is a race upload; type 1002 is a Director's Cut upload. Downloadable Director's Cut objects use type 2222. The client writes them to `current.i3d` and returns command -2 to the game. Race objects use type 1001, `ghost_in.dat`, and command -3. The recognized client's type 2223 filename is the literal `NOT USED !`; the service does not publish that type.

Download chunks carry `u32 total_size, start, inclusive_end, chunk_size`, then bytes. Normal downloads append `u32 object_id`; the provider bootstrap does not. Upload chunks may arrive out of order. Exact duplicates are harmless; overlapping or inconsistent ranges are rejected. A download token beginning with `701,` identifies a competitive race challenge. Practice downloads do not award points.

## Native directories and messages

A directory page begins with three bytes: record count, zero-based page index, page count. Directory pages then carry `u32 parent`. Each object is `u32 id, u16 kind, u16 billing, u32 value1..value4`, followed by two strings. The client has small fixed buffers: object names are limited to 20 bytes and player names to 12.

The client chooses its renderer by parent ID, independently of the displayed directory name:

| Parent | Native role |
| --- | --- |
| 1 | Main menu |
| 900 | Course directory |
| 912 | High scores / league table |
| 915 | Two-row challenge page |
| 918 | Result and outcome rows |
| 1201, 1202–1211 | Upload category and caption selection |
| 1301 | Player clips, a generic directory |
| 1401, 1402–1501, 920 | Guide category / clip download selection |
| 501 | Messages |

Challenge row 0 describes the opponent. Row 1 describes the current player and carries the course and downloadable opponent object IDs. Both rank strings must contain decimal digits; an empty string asserts in the native client. Result row 0 carries the uploaded time, cumulative monthly score and rank. Row 1 supplies the won/lost flag and absolute point delta. Negative scores are transmitted in the original 32-bit representation.

The local upload catalogue uses parent 1202 for ordinary clips and 1203 for guides. Type-2 category leaves 3000–3015 name the guide levels. The client echoes the selected category ID in the upload's second `u32` value; the server routes those clips to parents 1402–1417. This was verified with a native Caves upload carrying values `1, 3001`, then downloaded from parent 1403.

A message contains its body string, two type bytes, message ID, sender string and two `u32` values. Type 1 displays the welcome message; type 0 displays a challenge message with the native Revenge action. That action requests directory 915 with `sender,revenge`. The server restores the corresponding course from the latest completed winning challenge against the recipient, so revenge works after a fresh login.

The client caches received and sent messages in a Symbian stream file. `logincookie.dat` is also a Symbian stream, not a plain C string: a native five-character nickname has a one-byte descriptor-length prefix followed by its five characters. The setup helper leaves account cookies and saved games alone.

## Replay containers

Director's Cut files start with four `u32` values: snapshot frame, first frame, last frame and compressed snapshot size. A zlib stream expands to a 12,684-byte game snapshot. The remaining input block contains a four-byte value followed by 17 streams, each with a `u16` byte length. Optional camera data begins with `u32 1234` and five similarly length-prefixed streams.

A race begins with the packed layout `<IHHHIIIiiiH`: course ID, level, room, checkpoint count, yaw, excluded item mask, frame limit, start X/Y/Z and marker 0x1234. It is followed by checkpoint XYZ triples, completion time in milliseconds, a transformed time checksum, replay frame bounds, random seeds and the 17 input streams. See `arena/replay.py` for the checksum and bounds checks. The native game replays the reference input and compares the generated finish time before starting the live race; merely supplying a plausible time is insufficient.

The server validates the file structure, time checksum and registered course description. It does not run Tomb Raider's physics and is not an anti-cheat service. A losing client may upload the downloaded opponent replay. That submission records a loss but must not become the loser's personal best. Completion is committed once per downloaded challenge; a repeated final file returns the original result.

## Scope and unresolved historical claims

The implemented guide path plays full native recordings with pause, rewind and fast-forward. It does not yet reproduce the separate, simultaneously controllable “mentor Lara” described in contemporary player accounts, or a native offline library for reopening downloaded guides after a restart. Neither a valid mentor file format nor that reopening workflow has been established in the recognized binaries. These are not claimed as restored features.

The recognized game's clip loader at `0x0044a904` has one direct caller, at `0x00421960`. Its caller selects `current.i3d` for the Arena return code -2 or the built-in demo for -6, then clears the race flag before loading the recording. The nearby code that strips a `-r` filename prefix does not expose an additional command-line or menu entry. With the server stopped, a cold launch preserved the downloaded 642-byte `current.i3d`, but the Options screen offered no clip browser and Arena entered its connection screen before displaying directories. This narrows the missing offline workflow to access to the saved content, rather than file persistence or replay controls.

The game also reads an optional `adverts.dat` table to offer location-specific guide entry points. Its eight-byte records combine room in bits 0–7, minimum Z in 8–12, minimum X in 13–17, maximum Z in 18–22, maximum X in 23–27, and level in 28–31, followed by a `u32` directory ID. Tile bounds are inclusive and relative to the room's origin. The loader accepts at most 100 matching records per level, and the client's strategy argument retains only a 16-bit directory ID.

The original installation lacked this file. `author-guide-links` and the setup helper now support explicitly authored regional maps with validation and backups. A Caves room-0 record produced the native STRATEGY film icon. The left softkey launched `GSBAPP` in strategy mode, requested directory 1403 directly, and downloaded into the same full-recording player. This separate entry path also did not produce a second controllable Lara or an offline guide library. It does not justify patching the game into an invented guide mode.

Official courses, walkthrough recordings, original accounts and Nokia's unpublished scoring formula are unavailable. Local imports and the documented +10/-5 policy are explicit replacements. No ROM, game executable, extracted snapshot or recording is included in source control.

## Ashen Community and SNAP

Ashen uses Community SOAP at `/n-gage/axis/services/Community`, then legacy XMPP on TCP 5222. `createUser` returns `createUserResponse`; `authenticateUser` returns the numeric local account ID. The SDK asks for `jabber:iq:auth`, sends the lowercase SHA-1 of the password in the XMPP password field, retrieves its roster and publishes presence. The server authenticates that credential against a salted scrypt verifier. It derives the submitting account from the authenticated stream, not the caller's `snap_name` attribute.

Game class 42318 sends `segachat_send_event` to `reporter@ngage-auth`, event type `submit`. Its nine integer statistics are `level_1` through `level_8` and `game_total`. Personal bests only increase. Queries use `segachat_retrieve_req` to `retrieval@ngage-auth`, event type `topn`, with XML escaped inside `retrieve/request`. The native query selects `HIGHSCORES`, offset 0, limit 7, all-time period, natural ordering and CSV format. The response is `segachat_retrieve_resp`, with escaped text inside `retrieve/response`: status and message lines, a pipe-delimited query header, then `name|rank|score|0` rows. Empty boards return zero rows.

The original multilingual Ashen 1.0.6 executable and its bundled libraries work without binary modification. Its ArenaFoundation client waits for the legacy RGenericAgent stage EConnectionOpen (14). High Seize also waits for the subsequent EIfProgressLinkUp (1000), defined by the Symbian 6.1 interface progress range. These differ from modern RConnection KLinkLayerOpen (7000); the HLE connection must expose the legacy agent and interface stages in order. The setup helper configures host mappings only; import, port and SNAP callback patches for a different installation have been removed.

## High Seize 1.0.2 / Arena 2.01.054 investigation

The full multilingual 1.0.2 package contains the native Arena SDK and UI. The SDK uses the same Community endpoint but sends HTTP/1.1 `Expect: 100-continue`: it waits for the interim response before sending the SOAP body. Its initial valid zero-capacity TCP receive must complete successfully with a transfer length of zero; the following receive carries the actual HTTP response.

The observed startup method is `checkImei`, whose return is a typed `xsd:boolean`. The current probe returns false and the game offers registration or existing-account login. Native registration sends username, password, device identity, names, email, birthdate and recovery question/answer. Registration succeeded through the game's form. The current service retains only the account verifier; device binding and profile/recovery operations remain unfinished.

`authenticateUser2` differs from Ashen's older method: `authenticateUser2Return` contains a typed boolean followed by a typed string. Returning success and the canonical username was verified through subsequent native SNAP authentication and presence. A false boolean produces the native invalid-credentials error. `HeartBeat` runs while account forms are open. The menu polls `getNewAlertStatus`; its parser expects a plain boolean return. The probe currently reports no alerts.

### N-Gage 2.0 authentication

The Launcher on the 5320 posts `authenticateUser` to `/ngi/axis/services/NGICommunity` over HTTPS, with `gameClassId` 4444. Its response differs from the legacy Community endpoint: `authenticateUserReturn` contains `item` elements, with the first string `0` indicating success. Returning a numeric account ID directly produces the native invalid-credentials message even when the password is correct. `NAFAuthSrvr_V3`'s `CLoginXML` parser at linked address `0xb240` tracks the item index; its character handler at `0xb33e` compares item zero against the UTF-16 literal at `0xd440` and stores the authentication flag at object offset `0x74`.

The native Launcher accepted `["0", canonical_username]`, authenticated through legacy SNAP/XMPP, published presence and showed its green online indicator. These operations use the shared account store. The cookie also travels in the URL path, so request logging omits matrix parameters.

### N-Gage 2.0 shared profiles

`/ngi/axis/services/userprofile` accepts the native SOAP profile operations. Operation and response roots use their individual `http://www.nokia.com/ngp/...` namespaces; their children are unqualified. The schema metadata in `nafuserprofile.dll` defines ordered sequences and response choices. For example, `getMiniProfileResponse` contains either `miniProfile` or `ngpexception`; `getProfileResponse` has optional `user` and `ngpException`, with different capitalization. The profile request uses `lastSynchDate`, while the friends request uses `lastSyncDate`.

`arena.profiles` stores profiles, game history and friendship relationships against the canonical account IDs in the same SQLite database. Full profile reads and updates use the authenticated HTTP session, never a supplied username. Public mini-profiles contain the username, icon URL, three N-Gage point categories and game history. Friend details require an accepted relationship. Writes are validated before committing and preserve other games' history and the account's credentials. Dates and points without a source remain unset or zero. Friend subscription delivery, icon assets, reputation calculation and password recovery are still incomplete.

The native Launcher completed the profile request sequence, uploaded four installed games' last-played timestamps and saved an edited Motto through `updateProfile`. The native update includes `alertSubscription`, `privacySetting`, `ignoreUsersList`, `newsLetterSubscription`, `games` and `userIcon`; an empty built-in icon uses type `ASSET`. The returned `timeStamp` advances its subsequent synchronization requests. Server-side Motto changes were displayed with both a clean cache and the restored original cache after its pending upload completed.

The Launcher gives pending local changes precedence over downloaded editable fields. `playservermp.dll` stores `LocalProfileChanged` in its `LoginTable`. The profile response handler at linked address `0xb56e` tests this flag through `0x90fc`: the dirty branch retains editable local values and proceeds to upload, while the clean branch applies the downloaded profile. Successful upload completion at `0xb6b2` saves the timestamp and clears the flag at `0xb6bc`. A stale local Motto overwriting a server edit after offline gameplay was reproduced, then distinguished from a parser failure through the two download controls. The server follows this native whole-profile update policy; it does not claim field-level conflict merging.

The authentication server sends a plain HTTP GET availability probe to `/ngi/axis/services/NGICommunity` about every ten minutes. The native request contains only Host and User-Agent headers, with no cookie, query or matrix session identifier. Its `HeartBeatUtl` response callback at `0xa124` in `NAFAuthSrvr_V3` treats HTTP 401 as lost authentication. The service returns an empty HTTP 200 response without creating, authenticating or refreshing any account session. Treating this anonymous probe as session validation incorrectly logs the native client out. Authenticated SOAP operations continue to enforce their session requirements and expiry. The native timer clamps a configured interval below 60 seconds to 60 seconds (`0x897c`–`0x898c`). Ranking submissions are being restored separately; native friend messaging and game multiplayer remain unfinished paths.

Hooked On's native Arena update uses game class `58600` (SNAP presence `GCID="e4e8"`). Its `/ngi/servlets/rankings` upload is segmented: each pending fish or tournament journal event produces a submit containing `TOTAL_XP`, `TOURNAMENT_SCORE`, `FISH_WEIGHT`, `LOCATION_ID`, `TOURNAMENT_ID` and `FISH_ID`. A separate submit with those fields reports total XP; two more carry `TOTAL_MASS` and `TOTAL_ITEMS`. Each includes `$version` and `queryid`. A fresh save has no journal events and sends three reports, with zero scores and `LOCATION_ID=378939982`. Valid reports are stored individually in `ranking_reports`, keyed by the shared account ID, before confirmation. The response CSV has six header columns and places the numeric query ID in the second column, as required by `NAFRanking_V3` at `0xec8a`–`0xed38`; its operation token also drives the HTTP response dispatcher. These are snapshots reported by the game, not increments to catch totals. Native Hooked Update then completes 64 reads: TopN and nearby lists for XP, total weight, item count, six tournaments and 23 fish types. High-score rows contain name, rank, score and trailing metadata; the filtered board uses eight header fields and the unfiltered board seven.

Positive-save validation established that `TOTAL_MASS` and `FISH_WEIGHT` use 256 units per kilogram. Barracuda's `FISH_ID` is `3885652021`; The Hooked On Costa Rica Classic uses `TOURNAMENT_ID=3164354257`. Event reports leave unrelated scores and filter IDs zero, so the service must retain each report's filter scope and select personal bests rather than overwrite totals or sum retries. The native client sends only the three total reports on its next Update after accepting the event confirmations.

The retail `COTD.exe` save serializer at `0x5247c`, reader at `0x532b8` and upload loop at `0x848c0` identify the journal as `SECT/PHOD/EVNT`. `RYBI` contains the fish or tournament GUID, `MASA` contains the single fish's floating-point kilograms, `PPOI` contains tournament points and `AREN=1` marks an unsent event. The native upload clears `AREN`; normal game exit persists the cleared flags. GUID filters are derived by the client's 16-byte hash, not by interpreting a GUID word as an integer. The save uses nested four-byte tags and little-endian 32-bit payload lengths. Its first two bytes are the big-endian 16-bit sum of bytes after the four-byte file header. These findings enabled local, user-authorized test fixtures without changing game code, ROM data or leaderboard caches. Original saves and generated fixtures remain outside version control.

The native achievement request is `<player userName="…"><commands g="58600"><add id="35" ts="20260913:141429.3"/></commands></player>`. `NAFAchievement` at `0x85ba` requires HTTP 200 and a body beginning with `OK`; the comparison descriptor is at `0x8db0`. The service acknowledges only after committing validated achievements to the common account database. The `(game_class, user_id, achievement_id)` key makes retries idempotent and preserves the first reported earned time. The native request builder permits at most 34 entries per batch. Hooked's installed `AchievementTable` associates UID `0x2000AFBC` with 37 IDs, worth 1000 points in total; IDs 35 (Arena login), 36 (first stats update) and 37 are worth 10, 20 and 30 points. The service derives points from these definitions rather than accepting client-supplied point values. Binary and database offsets are recorded in local validation evidence. This records client-reported unlocks; it is not server-side proof of gameplay. Native acknowledgement is verified: the next login did not resend achievement 35, and completing the first ranking update generated achievement 36. The achievement definition also supplies NGPType: Hooked IDs 1–34 are single-player (1), IDs 35–37 multiplayer (2). This category is persisted with the awarded points; the initial six-column journal is migrated without changing earned times.

The original NAF ranking HTTP transport sends only Host, Content-Length and Content-Type headers, without a cookie or other account credential. Read-only `topn`, `getplayer` and `proximitylist` operations are public: a caller's source/name labels do not confer identity or require a session. Implemented board adapters still validate the query and supported filters. This is the private service's explicit access policy; absence of credentials in a capture alone does not establish the original service's policy. Score submission, match allocation and achievement writes require an account association, and private profile operations retain their separate authorization.

Cookie-bearing writes use normal Community sessions. For trusted local emulator runs, `--local-native-http` admits a credential-free score or achievement upload only from a loopback address with a currently authenticated SNAP connection for the same player and address. Closing or failing that SNAP login revokes the association. The option is off by default and does not authenticate individual local processes; a process on that host can claim another currently logged-in local player. It does not apply to private profile operations or remote HTTP writes. Public leaderboard reads require neither this flag nor a SNAP login.

High Seize's SNAP presence advertises game class `8db8` (decimal 36280). The package names `retrieval36280`, `reporter36280`, `im.hs.redlynx.sf.yav4.com`, and `bs01.hs.redlynx.sf.yav4.com`. Login and roster exchange work; game-specific lobby, game-room, messaging and score exchanges are still being recovered. High Seize is not yet claimed as a completed service.

### High Seize SNAP UDP login

The original `snapcomm.dll` identifies itself as kkClient 2.1. Its bootstrap endpoint is `bs01.hs.redlynx.sf.yav4.com:9090`. Integers on this wire are big endian. A datagram contains a 16-byte header, body and trailer `ba476611`. The header is `u16 flags_and_length, u16 operation_and_query_id, u32 sender, u32 sequence, u32 acknowledgement`. Length occupies the low ten bits and includes the header, excluding the trailer. The low seven operation bits select the handler; its upper byte identifies a query. Flag `0x8000` marks reliable delivery and `0x4000` acknowledges an outgoing reliable sequence. The first frame's `0x0800` flag indicates an aggregated datagram: subsequent frames have individual headers and lengths, but do not each repeat this flag. They share one trailer and the first nonzero reliable sequence. Native room creation supplied a four-frame attribute update that established this distinction.

Authentication starts with operation 44: 40-byte username, 60-byte JID, game class 36280 and network/options fields. Operation 64 is a 280-byte Blowfish ECB challenge encrypted with the ASCII key `SNAP-SWAN`. Its plaintext has status and salt length at offsets 0 and 4, up to 128 salt bytes at 8, encrypted and actual nonce lengths at 136 and 140, and the encrypted nonce at 148. The inner key is raw SHA-1 of password bytes followed by salt. The service uses an empty salt so that the already authenticated XMPP verifier can serve as this key; each challenge has a fresh random nonce. The verifier stays in memory only for the authenticated XMPP connection and is removed on close or failed reauthentication.

The client returns operation 65, a 136-byte `SNAP-SWAN` ciphertext. Its plaintext has actual nonce length at 0 and nonce bytes at 8; trailing bytes are not initialized by the native client. A matching proof receives operation 45 with flags `0x7000`, sequence 1 and an acknowledgement of the proof. Its 320-byte encrypted body carries username at 0, IPv4 address at 40, UDP port at 44, status at 48, custom data length at 52 and assigned identifier at 56. This acknowledgement stops native proof retransmissions.

The redirected client sends operation 1 to the game endpoint. Operation 41 with three `u32` values (port, reserved zero, assigned identifier) completes this second login, after which the original client requests lobbies with operation 71. The native tests used port 9090 and identifier 1. No plaintext passwords or extracted game binaries are included in this project.

### High Seize lobby and room investigation

Operation 71 replies contain three `u32` values followed by 36-byte lobby records; the third value is record count. A record contains a 16-byte name, member count at 16, an unused-by-this-client field at 20, maximum members at 24, status at 28 and lobby ID at 32. `arenaframework.dll` at `0x10005f8c` establishes these offsets. A native create-room flow selects a lobby and sends reliable operation 6 with its ID, accompanied by an operation 13 player-state update. The generic operation 40 reply body `(6, lobby_id)` completes joining the lobby.

A native room request is operation 4 with name and game attributes. Generic reply `(4, room_id)` is accepted, then the client sets `ARNA`, `ARNB`, `ARNC` and `ARND` via four aggregated operation 8 frames. Each operation retains its query ID in the response. These room exchanges are still diagnostic probes: creation is not complete until the original client reaches its player waiting room, and multiplayer gameplay has not yet been verified.

### High Seize room and dedicated game data

Native lobby enumeration uses operation 71. Its reply begins with three `u32` values (status, returned count, total count), followed by 36-byte records: name[16], members, reserved, capacity, status, ID. Lobby events have flag `0x1000` in addition to the normal `0x2000` control flag. Generic operation 40 completions retain the query's upper operation byte and contain `u32 original_operation, u32 result`.

Room creation reaches the game only after room-created operation 4, its query completion, own-user-joined operation 6, and room attribute operation 8 with `u32 room_id, char[4] HOST, u32 host_user_id`. Client attribute writes use `ARNA` through `ARND` and `STAT`. These handlers are still diagnostic; persistent rooms, admission, host departure and broadcast membership are not yet implemented in `arena.snap`.

The dedicated-server channel carries outgoing SNAP operation 17 and incoming operation 15. The game socket opens on its first incoming game-data callback. A valid first heartbeat supplies this callback; sending an empty SNAP body is invalid because the game reads a four-byte length unconditionally.

Inside SNAP, game data switches to little endian. A `u32` gives the following DataPartition stream size. Single partitions have `u8 type=0, u16 payload_size_including_markers`. Multipart partitions have `u8 type=1, u16 message_id, u16 part_index`, with `u16 part_count` only at index zero, followed by that same length. Each partition inserts `0xfe` before its data and after the first floor(data_length / 2) bytes. Native outgoing parts carry at most 768 data bytes. All parts must be acknowledged at the SNAP level, even before the complete game message is assembled; otherwise the native client exhausts retries and closes the game socket. `arena.highseize` implements the codec and bounded per-peer reassembly.

The reassembled game packet is `u8 kind, u8 source, u16 body_length, u32 destination_mask`, then its body. Before assignment the client uses source `0xc1`; after host handshake it uses the assigned one-based player slot. Kind 12 announces a host with `u32 0xdeaddeaf`, or a joining client with `0xdeadbeef`. Server kind 11 is a heartbeat; native kind 12 replies with its current slot about every 14 seconds. The client closes the connection after 60 seconds without a heartbeat.

Kind 17 performs a four-state handshake with body `u16 next_state, u16 data_length, data`. The host initially sends state 1 with 198 bytes of GameSettings. It then receives state 2 with its Player, state 3 with GameSettings, and state 4 with a linked list of remote Players. An empty state-4 value leaves the initially empty remote-player object uninitialized, so a host can create a room with no other players.

GameSettings serialization is eight `u32` fields, two one-byte booleans, another `u32`, a 32-byte name and 128 additional bytes. The fields are read into native offsets 0x2a4 through 0x2c8, 0x204 and 0x224 respectively. The server probe retains the host's settings rather than inventing map data. A minimal Player has a zero next-player-present byte, `u32 slot, team, skill_points`, name[32], `u32 nationality`, a player flag byte, and a profile-present byte. A present next player or profile recursively adds its serialized object. Slots are 1-based; zero underflows the client's player-array index. A no-profile value is explicitly supported by the native player-to-commander conversion.

Ready sends game kind 18: `u16 subtype, u16 data_length, u32 player_slot, data`. Subtype 1 carries the serialized commander; the observed local commander contains 1,028 bytes starting with `CMM01`. Subtype 2 with no data announces that player's commander setup completion. The native client also applies its own update locally. With these packets acknowledged and regular heartbeats, the host proceeds to the team-selection screen. Joining another native client and completing the battle launch remain unverified.

High Seize also requires the Community HTTP session cookie. `cafmlogin.dll` at `0x10004a9c` reads `Set-Cookie`, takes its value before the semicolon, and passes it through FMKernel virtual slot `0x68`; this retains the cookie in the Arena framework at object offset `0x9a0`. On return from a game room, FMKernel initialization at `0x10000dac` retrieves and copies that descriptor without a null check. Omitting the cookie allowed initial login and room setup but crashed at EUSER `TDesC8::AllocL` on reentry. The service now issues opaque random `JSESSIONID` cookies with bounded, expiring server-side sessions and reuses them on subsequent HTTP connections. This fix belongs in the private service; no null-pointer workaround is needed in the emulator or game.

An incoming reliable server game-data frame was also tested directly: SNAP operation 15 with flags `0xa000` and sequence 26, carrying a valid High Seize heartbeat, produced the original client's operation-0 acknowledgement with flags `0x6000`, sequence zero and acknowledgement 26. The final room transport must retain/retry reliable server events until acknowledged; the diagnostic probe's usual `0x2000` events do not yet implement that reliability policy.

Filtered room search is SNAP operation 73. Its successful reply has the same three-word query header as lobby listing, then 40-byte extended room records: name[16], lobby ID, member count, reserved, status, capacity, room ID. The original Arena callback path (`0x1001093c` → interface slot `0xc0` → `0x10018e2c` → `0x10006068` → `0x1000527c`) selects the extended parser at `0x10005428`; it advances 40 bytes per record. Nonextended room records omit the lobby ID, so room status is at 24 and capacity at 28. Lobby records use the opposite order for those two fields. A native peer displayed the existing host's High Seize room after receiving a correctly encoded extended record. Both native clients then completed room admission when the extended record referred to the published lobby ID 1. Returning lobby 0 caused the SDK to dereference a missing lobby name while leaving its room browser.

The native SNAP client can coexist with another local emulator: it starts binding UDP 2000 and increments the port after a negative bind result (`snapcomm.dll` `0x10002200`–`0x10002238`). Two original clients authenticated concurrently on 2000 and 2001 using the emulator's propagated bind errors; no port virtualization or game patch was necessary.

The joining client announces `0xdeadbeef`, then accepts handshake states 2, 3 and 4 with its own slot, host settings and host Player. The two native clients reached commander settings and the host displayed the second player. Odd-sized DataPartition payloads split at floor(length / 2), as established by integer division at `0x10003ff8`; rounding upward corrupts one byte around the marker. The first visible symptom was a changed character in player names. The codec now covers this case. These room and setup responses remain diagnostic until reliability, departure and battle data routing are implemented and validated.

The Player byte after nationality is the host flag, read into native offset `0x44` and copied to the UI player at `0x9d`; initialization is set separately by deserialization. Sending that flag for a joiner incorrectly grants host UI controls. A cold two-client test with only slot 1 marked as host displayed matching names, distinct teams and the appropriate host/peer screens, and automatically exchanged both commanders and ready states.

GameSettings fields, in wire order, are mission style, game type, matchup mode, player count, skill points, turn time, host, map sub-index, ranked byte, fog byte, commander setup mode, game name[32] and mission ID[128]. Initial host requests leave game type, host and mission ID unresolved. Echoing that empty mission reaches a null mission-data lookup at `0x100959ec` and crashes both clients at `0x1008a1f8` when launching. `0x10078b94` names the fields and identifies GPRS as game type 6; menu dispatch around `0x1000ea7c` distinguishes short style 2 and normal style 3. The local package supplies short mission IDs MPS1–MPS22 and normal mission IDs MPN23–MPN34, grouped by supported player count. The server must resolve the selected map and return complete settings before battle launch. With these resolved settings, two original clients entered MPS1 on separate iOS simulators without the mission lookup crash.


### High Seize battle messages and completion investigation

Game packet 16 carries a serialized battle message: `u32 size_after_length, u32 kind, u32 message_id, u32 player_slot, u32 turn, u8 flag, u32 pre_crc, u32 post_crc`, then type-specific data. The header is 29 bytes; the first size excludes its own four bytes. Both native clients send kind 26 (synchronization) after map initialization. The dedicated server then supplies kind 23 (battle begin). The enclosing GamePacket destination bit 0 must be set for client delivery; the native receiver at `0x1000c5a4` maps this bit to message origin 2. An unset bit gives origin 3: it can leave the initial wait loop without starting the visible battle. The server-marked begin packet advanced both clients to the map.

The native message-name switch identifies kind 10 as end turn, 16 as surrender, 21 as acceptance, 22 as rejection, 23 as battle begin, 25 as end game and 26 as synchronization. These values are separate from the outer game and SNAP operations. An end-turn request from the active player requires a new server message with source 0; forwarding that client request alone does not authorize a turn change. Both clients advanced through several turns with server authorization. Acceptance and rejection have an additional `u32` original message ID.

The game's global End current game menu leaves its SNAP room and returns to Arena rather than showing a surrender result. In a diagnostic match, slot 1 used that menu. The remaining client required a source-1 end-game message (kind 25, four-byte reason 0) to mark that player defeated, followed by the server's own end-game message. A debugger read confirmed player 1 inactive and native winner mask 4 (slot 2). The original peer then displayed Mission successful and battle-info pages naming slot 1 as loser and slot 2 as winner. Both clients returned to Choose Mode. This was a recovered diagnostic departure path; automatic room departure, normal surrender, result storage and ranked reporting still require implementation and validation.

Movement kind 0 serializes unit ID, path-node count and path cost as three little-endian `u32` values, followed by signed 32-bit `(x, y)` pairs (`0x10096e74`). An original client moved unit 3 along `(2,2) → (1,2) → (0,2)`, producing flag 1, pre-CRC `0x32beb9c7` and post-CRC `0xcf410638`, then kind 5 Wait for that unit. Attack kind 1 carries attacker and defender IDs (`0x10038110`); the clients calculate combat effects locally.

That first movement trial exposed two diagnostic transport errors. The probe relayed the original packet with destination bit 0 clear before sending its corrected server-origin copy. Per-source ID deduplication discarded the latter. `MessageTimeline::insert` (`0x10092048`) accepts origin 2, leaves local/origin-3 entries pending, and removes pending entries when the next server event arrives. In addition, accepting Wait alone does not accept the earlier move: `MessageTimeline::accept` (`0x100922d4`) marks only the specified ID. The native server path commits a stored move before the following action (`0x1003cbe0`). Read-only heap snapshots after the flawed trial showed unit 3 back at `(2,2)` on both clients; this trial is a failure, not evidence of persistent coordinate synchronization. Corrected routing and paired confirmations require a fresh native trial.

In the corrected one-way trial, both original clients retained unit 3 at `(1,2)` after its Move and Wait were individually accepted. Read-only snapshots matched all ten map-occupying units' IDs, owners, coordinates and HP. The subsequent reverse trial exposed a separate missing handshake: slot 1 dropped slot 2's first Move (ID 1), accepted Wait (ID 2) and failed CRC verification. The native channel constructor clears only five bytes at its five-word per-source ID table (`0x1000bfa4`, EUSER ordinal 416). Slot 1's source-2 entry still contained `0x6572702f`; it treated Move 1 as a duplicate. The receiver always writes the received ID back, even after dropping a duplicate, so Wait 2 was accepted without its preceding move. Forwarding each participant's native kind-26 synchronization message with ID zero before Begin resets that participant's receive sequence through the original channel code. This required startup exchange was omitted by the diagnostic server; the game and emulator binaries are unchanged.

A fresh two-client trial with both participant synchronizations before Begin passed forward and reverse movement, then a native attack. Slot 1 moved Sword unit 3 from `(2,2)` to `(1,2)`; slot 2 moved Sword unit 4 from `(7,2)` to `(5,2)`. After another turn, slot 2 moved to `(4,2)` and attacked Mortar unit 34 at `(3,2)`. Its Move was ID 5 and Attack was ID 6, both on turn 3. Attack payload `0400000022000000` identifies attacker 4 and defender 34. Both clients independently reduced the mortar from 100 HP to 47 HP and retained the attacker at 100 HP. Paired read-only snapshots matched turn, active player, and all ten map-occupying units after each of the three checkpoints. Transported units are outside this grid inspection.

Moving the orchestration into the service exposed the distinction between receipt and ordered delivery in SNAP. `snapcomm.dll` resets its reliable receive sequence to zero at `0x10002526`–`0x10002530`. The dispatch queue at `0x10008b50`–`0x10008b94` only releases the exact next sequence and increments it after delivery. An ACK therefore does not prove that a reliable event reached the game callback. Starting server reliable events at 3 left the original client waiting for lobby data even after its profile had been retrieved. Reliable and unreliable traffic require independent counters, with the reliable stream starting at zero; heartbeats must not introduce gaps in it. The production transport now applies this rule, queues one unacknowledged server event at a time and buffers reordered native datagrams within a bounded window.

The same trial then used Options → Surrender in the active player's original UI. Slot 2 sent kind 16, ID 7, turn 3, with an empty payload. The diagnostic service relayed and accepted it, then automatically sent server kind 25 with reason 2 to both clients. Slot 1 displayed Mission successful and slot 2 Mission failed. Both Battle info sequences named the same winner and loser, showed two turns per player, zero winner losses and seven loser losses. The loser elapsed-time field differed by one second (`13:32` versus `13:31`); the common total was `13:35`. Elapsed-time authority remains unresolved. This establishes native combat and surrender through the diagnostic orchestration, not durable results, ranked reporting or a completed production room service.

The native client acknowledges reliable sequence zero correctly. Lobby screens send no periodic UDP request of their own; the transport therefore sends a reliable no-op every 30 seconds and uses its acknowledgement to keep an idle session alive. The first dedicated-game heartbeat must follow the attachment-completion event in the reliable queue. An unreliable first heartbeat bypassed queued control replies and reached the client before its game channel was ready, causing the native connection timeout. Sending that first heartbeat reliably allowed the original host to exchange settings and reach commander/team setup. Later game heartbeats retain their independent unreliable counter.


The shared `ngpsglobal` and per-game `ngps` boards derive their totals from the same account achievement journal. They support public all-time TopN and nearby lists. The global board ignores the request's incidental game class; a per-game board filters that class. Global rows are `name|rank|singlePlayer|multiplayer|community|total|metadata`; game rows omit the community column. Community points are zero until a community-point source is implemented. The seven-field header retains query ID at index 1 and board at index 4. `playservermh` global parser `0x107f2`, per-game parser `0x1096a`, and its UsersTable layout establish the distinct point fields; `playserverach` synchronizes single-player and multiplayer values into NGPType 1 and 2. Unsupported time periods, filters and friend lists are rejected rather than returning an unfiltered board.
